# Sthanam — Payment Architecture & Provider Handoff (Step 3 & Step 7)

## 1. Overview & Honest Limit

A plain UPI QR cannot be confirmed automatically by the browser alone. Browser-side polling of bank accounts is technically impossible without an aggregated payment gateway or payment aggregator (PA/PG) such as Razorpay, Cashfree, or PhonePe PG.

In **Step 3 (Frontend)**:
- We implemented the complete payment UI step inside the reservation flow with a scannable standard NPCI UPI QR code.
- We built the robust domain **Payment State Machine** with a 5-minute reservation hold.
- We established the **`PaymentProvider`** abstraction interface.
- We implemented **`DemoPaymentProvider`** to allow end-to-end testing, realistic delay simulation, and state transitions (`awaiting_payment` → `processing` → `paid` / `failed`).
- Simulation buttons are guarded by config (`isDemoProvider && import.meta.env.MODE !== 'production'`) and cannot be displayed in production.

In **Step 7 (Backend & Infrastructure)**:
- The real payment gateway (Razorpay / Cashfree) is plugged in on the backend.
- The backend verifies cryptographic webhook signatures and marks the payment as paid.
- **The frontend never decides whether a payment succeeded.**

## 2. Payment Domain State Machine

```
              ┌───────────────┐
              │    created    │
              └───────┬───────┘
                      │ createPayment(bookingDetails)
                      ▼
              ┌───────────────┐
      ┌──────►│awaiting_paymnt│
      │       └───────┬───────┘
      │               │ webhook / user action / poll
      │               ▼
      │       ┌───────────────┐
      │       │  processing   │
      │       └───┬───┬───┬───┘
      │           │   │   │
      │  ┌────────┘   │   └────────┐
      │  ▼            ▼            ▼
   ┌──────┐       ┌──────┐    ┌─────────┐
   │ paid │       │failed│    │ expired │
   └──────┘       └───┬──┘    └─────────┘
                      │
               "Try Again"
```

### State Definitions:
1. **`created`**: Payment record initialized before hold allocation.
2. **`awaiting_payment`**: Spot bay held for pilgrim. 5:00 countdown timer active. UPI QR presented.
3. **`processing`**: Transaction broadcast or webhook received; awaiting settlement verification.
4. **`paid`**: Payment confirmed cryptographically. Booking moves to confirmed pass with QR ticket and receipt.
5. **`failed`**: Bank decline, user cancellation, or invalid VPA. Pilgrim can "Try again" or change method.
6. **`expired`**: 5-minute hold elapsed without payment confirmation. Parking bay released back to the general map.
7. **`cancelled`**: User explicitly cancelled checkout or closed hold; spot bay returned to inventory immediately.

## 3. Standard NPCI UPI URI Specification

The UPI QR code generated by Sthanam follows the official NPCI UPI Deep Link specification:

```
upi://pay?pa=<VPA>&pn=Sthanam&am=<amount>&cu=INR&tn=<bookingRef>&tr=<txnRef>
```

### Example:
```
upi://pay?pa=sthanam@upi&pn=Sthanam&am=281.00&cu=INR&tn=NPC-7F3K9&tr=TXN_NPC-7F3K9_K9LP2M
```

- **`pa`**: Virtual Payment Address (VPA) from `import.meta.env.VITE_UPI_VPA` (default placeholder: `sthanam@upi`, flagged "demo").
- **`pn`**: Payee Name (`Sthanam`).
- **`am`**: Amount in Indian Rupees with 2 decimal precision (e.g. `281.00`). Internally stored in integer **paise** (`28100`).
- **`cu`**: Currency code (`INR`).
- **`tn`**: Transaction Note / Booking Reference (`NPC-7F3K9`).
- **`tr`**: Merchant Transaction Reference ID (`TXN_...`).

## 4. Backend Step 7 Implementation Contract

When implementing the backend in Step 7, wire the real payment gateway (Razorpay or Cashfree) using the following flow:

### 4.1 Order Creation (Server-Side)
- Endpoint: `POST /api/v1/payments/create-order`
- Authentication: Required (`Bearer <JWT>`)
- Request Body:
  ```json
  {
    "bookingId": "b_123456",
    "amountPaise": 28100,
    "currency": "INR"
  }
  ```
- Backend Logic:
  1. Call Razorpay Orders API: `razorpay.orders.create({ amount: 28100, currency: 'INR', receipt: bookingId })`.
  2. Insert record in PostgreSQL `payments` table with status `awaiting_payment` and `expires_at = NOW() + INTERVAL '5 minutes'`.
  3. Return `{ orderId, paymentId, upiIntentUrl, amountPaise, expiresAt }` to the client.

### 4.2 Webhook Signature Verification (Crucial Security Rule)
- Endpoint: `POST /api/v1/webhooks/payment`
- Gateway: Razorpay / Cashfree webhook trigger
- Security:
  ```javascript
  const crypto = require('crypto')
  const expectedSignature = crypto
    .createHmac('sha256', process.env.RAZORPAY_WEBHOOK_SECRET)
    .update(JSON.stringify(req.body))
    .digest('hex')

  if (req.headers['x-razorpay-signature'] !== expectedSignature) {
    return res.status(400).send('Invalid signature')
  }
  ```
- Transition on valid `payment.captured`:
  1. Check idempotency: If payment is already `paid`, acknowledge with `200 OK`.
  2. Mark payment in database as `paid`, recording `gateway_payment_id` and `paid_at`.
  3. Update `bookings` table: change `status` from `payment_pending` to `upcoming`, set `payment_status = 'paid'`.
  4. Broadcast event via WebSocket / Server-Sent Events (SSE) to notify client browser immediately.

### 4.3 Safety Guarantees
- **No secrets in frontend**: Gateway API keys with secret privileges (`rzp_live_secret`, webhook secret) must NEVER touch frontend code.
- **Frontend never decides success**: The frontend only listens for server confirmation via SSE/polling or client redirect.

## 5. Frontend PaymentProvider Interface

All frontend payment providers implement `src/services/payment/provider.js`:

```javascript
class PaymentProvider {
  createPayment(bookingDetails): Promise<{ paymentId, upiIntentUrl, amountPaise, amountRupees, expiresAt, vpa, bookingRef, txnRef }>
  getStatus(paymentId): Promise<{ paymentId, status, paidAt, failureReason, amountPaise, expiresAt }>
  cancel(paymentId): Promise<boolean>
  subscribe(paymentId, listener): () => void
}
```

To switch to the real backend in Step 7, configure:
```env
VITE_PAYMENT_PROVIDER=backend
```
and register the `BackendPaymentProvider` which proxies calls to `/api/v1/payments/*`.
